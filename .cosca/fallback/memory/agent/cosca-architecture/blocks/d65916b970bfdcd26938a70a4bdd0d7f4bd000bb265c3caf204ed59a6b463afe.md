### 2026-07-30 — F9.4 Knowledge Aging Gatilhos design

**Técnica**: Design de sistema de gatilhos de revalidação automática de conhecimento, com 4 categorias de triggers (freshness, contradição, evento externo, schedule), pipeline de 6 passos, e integração com F1.4/F1.6/F9.2.

**Domínio**: architecture, knowledge-aging, revalidation, wisdom-decay

**Contexto**: Implementação do F9.4 como engine de "despertador do conhecimento" — quando freshness cai abaixo do threshold, dispara revalidação automática. Complementa o F1.4 Wisdom Decay (que calcula freshness) com ação (que cria tasks, notifica, deprecia).

**Aprendizados**:

1. **F9.4 é complementar ao F1.4, não redundante**: O F1.4 calcula o freshness score e classifica. O F9.4 AGE — cria tasks, assigna agentes, notifica o Don, deprecia. Sem o F9.4, o freshness score é apenas informação passiva. A separação é saudável: cálculo numérico (F1.4) vs engine de ação (F9.4).

2. **Quatro categorias de gatilhos com prioridades distintas**: Temporal (T1-T5, freshness-based), Contradição (C1-C3, conflitos ativos), Evento Externo (E1-E6, novas versões/CVEs/migrations), Schedule (S1-S4, revisão programada por categoria). Cada categoria tem prioridade (P0-P2) que determina canal de notificação e prazo. Isso permite tratar eventos de segurança (P0, imediato) diferentemente de revisão STABLE (P2, 90 dias).

3. **Escalação progressiva previne depreciação silenciosa**: O pipeline de 6 passos inclui escalação automática: T1 (30d) → T2 (7d) → P0 (7d) → depreciação. Cada passo dá uma chance de revalidar antes de perder o learning. Sem escalação, learnings seriam esquecidos até virarem pó.

4. **Don override é essencial para conhecimento imortal**: Learnings `#constitutional`, `#immutable` e `#kernel-identity` não podem deprecisr — são a identidade do sistema. O override `keep_forever` congela o freshness e desativa gatilhos. Mas override excessivo (>5%) desvirtua o sistema.

5. **Depreciação NUNCA é exclusão — learning vai para learning_history**: O learning original é preservado com tag `#deprecated` e referência para substituto. Isso mantém a rastreabilidade histórica e permite auditoria de "o que sabíamos e quando".

6. **Integração com F1.6 é bidirecional e virtuosa**: Quando o F9.4 deprecia um learning stale, a entropia (F1.6) REDUZ porque stale_knowledge cai. Isso cria um ciclo virtuoso: gatilhos limpam conhecimento → entropia cai → decisões baseadas em conhecimento ficam mais confiáveis → efficiency_score (F2.1) sobe.

7. **Notificação P0 vs P1 vs P2 é o fator mais crítico de usabilidade**: Se tudo notifica o Don como P0, Don ignora. Se nada notifica, learnings morrem sem supervisão. A chave é: P0 = "ação imediata ou perde conhecimento", P1 = "resumo semanal", P2 = "log do agente". O Don só vê o que realmente precisa ver.

8. **Exemplo real com L11 (Onda 6) validou o design completo**: Simulei 4 cenários (uso regular, esquecimento, contradição, evento externo) com o learning real L11 do Kernel. Cada cenário demonstrou um caminho de gatilhos diferentes, validando que a matriz cobre todos os casos de uso do mundo real.
