| **Learned** | A ORDEM OFICIAL do Professor (não pular): F6 Storage → F7 Capability Model → F8 Workload Model → F9 Microbenchmark Framework → só depois o resto. A lógica por trás: F1-F5 respondem "ONDE estou"; F6 "QUAIS recursos existem"; F7 "O QUE consigo fazer"; F8 "O QUE preciso fazer"; F9 "QUANTO consigo realmente fazer". F6 STORAGE: descobrir o terreno (NVMe/SSD/HDD: identity, capacity, filesystem, mount, visibility, read/write capabilities, queue characteristics, environment restrictions) — com reported ≠ visible ≠ usable ≠ measured. F7 CAPABILITY MODEL (a transformação central): o Cosca deixa de ter "CPU=Ryzen, GPU=RX 6700 XT, RAM=31GB" e passa a ter uma MATRIZ: compute.cpu.avx2=available, compute.gpu.vulkan=reported, compute.gpu.rocm=unavailable, compute.gpu.compute=unverified, memory.capacity=available, storage.nvme=available — cada capability carrega: STATUS, SOURCE, EVIDENCE, CONFIDENCE, ENVIRONMENT, TIMESTAMP. "Isso pode virar uma das estruturas centrais do Cosca." F8 WORKLOAD MODEL: cada workload (LLM inference, embedding, vector search, image generation, video encoding, compilation, database, scientific) DECLARA requisitos (CPU, SIMD, memory bandwidth, GPU optional, VRAM optional, storage) → o Cosca compara WORKLOAD REQUIREMENTS × CAPABILITY MODEL × AVAILABLE ENVIRONMENT → CANDIDATE EXECUTION PLAN. F9 MICROBENCHMARK (só depois): o benchmark deixa de ser "vamos medir a máquina" e vira "vamos medir o que importa PARA ESTE WORKLOAD NESTE AMBIENTE" (ex: embedding → CPU SIMD + memory bandwidth + cache + vector throughput → MEASURED → workload profile → decision). A LEI DO COSCA (regra de ouro): "BENCHMARK NÃO ALTERA FACT. BENCHMARK PRODUZ MEASURED." Se FACT=31GB RAM e hoje mede 37GB/s e amanhã 42GB/s — a RAM não virou 42GB/s. Essa separação é o que evita CORRUPÇÃO EPISTEMOLÓGICA. O fluxo final: WORLD→OBSERVATION→CAPABILITY→WORKLOAD→EXPERIMENT→MEASURED→DECISION — a primeira ponte verdadeira para o cérebro de decisão. |
