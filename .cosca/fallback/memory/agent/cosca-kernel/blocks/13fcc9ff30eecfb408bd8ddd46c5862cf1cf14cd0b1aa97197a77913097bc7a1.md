# L346 — Campanha FASE 8: recall REAL (corpus, int8 vs float32 oracle)

## Experimento
TestCampaignRecallReal: 200 queries = vetores REAIS de chunks do knowledge.db
(13.914 vetores, dim 768, nomic/embedding real), float32 como ORACLE (flag
OFF) vs int8 (flag ON), K=50, mesmo indice. Condicao documentada: query =
vetor de um chunk do corpus (top-1 esperado = o proprio chunk).

## Resultados
conteudo@50 = 0.8666 (int8 top-50 contem 86.7% do oracle top-50)
distintos@50 = 0.5821 (itens < 0.99 do oracle no int8 top-50 — penalizado:
o int8 top-50 lota de quase-empates)
jaccard50 = 0.8205 (conjunto de vizinhos unicos — medida justa, PASS >= 0.80)
NDCG@10 = 0.9010
top-1 mudou 48% — TODOS em empates (gap < 0.02), NUNCA inversao com gap real
max err = 0.0147, mean err = 0.0028

## DESCOBERTA DO CORPUS (independente do int8)
- 13.914 vetores, apenas 9.184 DISTINTOS = 34% de embeddings duplicados!
- 44.7% dos itens do oracle top-50 tem score >= 0.99 (quase-empates)
- O ranking de top-50 e estruturalmente instavel: o proprio ORACLE escolhe
  arbitrariamente entre os empatados. O recall de RANKING (top-lim vs
  top-lim) mede a loteria, nao a qualidade do int8.
- Acao recomendada: deduplicacao do corpus (chunks repetidos) — projeto a
  parte, melhora a qualidade do RAG INDEPENDENTE do int8.

## Conclusao do contrato (epistemologia)
- O int8 preserva o CONJUNTO de vizinhos (jaccard 0.82, NDCG 0.90) e o top-1
  com gap real. A ordem entre quase-empates (44.7% do corpus) e instavel
  ate no oracle — quem precisar de ordem exata: flag OFF (float32) ou int16.
- Licao de metrica: recall de ranking com corpus duplicado mede a loteria —
  usar Jaccard de ids unicos (conjunto) + separar empates (gap < erro).
