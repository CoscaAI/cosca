| **Learned** | **(1) A chave do workqueue k8s é que ele guarda STRINGS (chave), não objetos: o TaskQueue mantém `tasks[key]` para lookup e a fila só orquestra `planID\x00taskID` — o NUL evita colisão entre plan/task IDs.** **(2) O retry rate-limited (`AddRateLimited` = `AddAfter(limiter.When)`) é superior ao `time.Sleep` inline porque libera o worker durante o backoff: no design antigo o worker DORMIA segurando a vaga; agora ele devolve a chave à fila e processa outra task.** **(3) A política `handleErr` (NumRequeues < maxRetries → retry; senão Forget + terminal) é o contrato completo de retry em ~10 linhas — o `Forget` no sucesso reseta o backoff pra próxima falha começar do zero.** **(4) Descobri que o TaskQueue era ÓRFÃO (zero usos no código, zero testes) — infraestrutura construída na Fase 3 do L153 mas nunca wireada; o refactor o tornou um componente testado e reutilizável, mas o ganho real de runtime está no RecoveryLoop (que É usado pelo StepRunner).** **(5) O delaying loop do workqueue (goroutine com timer resetável + heap por readyAt + canal de wakeup) é o ponto mais sutil de concorrência — testar com `-race` e margens generosas nos timings evita flakiness. |
