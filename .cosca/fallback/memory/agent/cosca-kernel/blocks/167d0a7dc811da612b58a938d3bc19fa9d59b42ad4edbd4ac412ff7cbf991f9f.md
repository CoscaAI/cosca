TODAS as 20 combinações de blocking ficaram ABAIXO do baseline: B32_W4=6.3, B32_W16=10.6-10.8, B64_W16=10.5, B128_W16=10.6-10.8, B256_W16=10.2, B512_W16=10.5-10.6 (GB/s 32.3-33.2). CONCLUSÕES COM EVIDÊNCIA: (1) BLOCKING NÃO AJUDA — PIORA: o aninhamento extra de loops (bloco→vetor→dimensão) custa mais que a localidade ganha; todas as 20 configs < baseline. (2) WORKERS IMPORTAM: W4=6.3 → W8=8.5-9.3 → W12=10.0 → W16=10.5-10.8 (escala com workers) MAS nunca alcançam o baseline de produção, que já usa W=16 com chunking próprio (scoreParallel). (3) O BASELINE DE PRODUÇÃO JÁ É O ÓTIMO LOCAL: 12.4 Mvec/s / 37 GB/s — o chunking existente supera qualquer blocking manual. (4) TETO ~37-38 GB/s CONFIRMA REGIME MEMORY-BOUND (próximo dos ~41-43 GB/s observados antes). (5) POR QUE O SWEET SPOT DE CACHE NÃO APARECEU: cada vetor é lido UMA VEZ, sequencialmente — não há reutilização de dados entre vetores; blocking só adiciona overhead de loop sem criar localidade reutilizável. A lição do Professor (uma mudança por vez) funcionou: eliminamos blocking com dados. |
