# L341 — Integracao do fast path int8 no indice L311 (produto)

## O que foi feito
O kernel AVX2 (L339) virou PRODUTO no InMemoryIndex (internal/vector/index.go):
- indexGeneration ganhou vecs8 []int8 (pad 16), sums8 []int32 (correcao de
  bias -128*sumR), nb []float32 (norma² EXATA do float32, para a
  normalizacao final nao degradar com a quantizacao).
- Conversao na carga: round(v*127) clampado [-127,127], uma vez por geracao.
- score8/scoreParallel8/scoreRange8: dot8BiasDot por row, score =
  dot8/(127²·‖q‖·‖r‖). Kernel exige len%16==0 — dimPad resolve.
- Flag int8Enabled (default ON; SQLiteVecConfig.DisableInt8 para desligar;
  SQLiteVec.SetInt8Enabled(bool) em runtime). Fallback float32 automatico
  quando desligado; SQL scan segue como fail-safe final.
- Testes: int8_recall_test.go (recall + pad + boundaries); oracle tests de
  paridade bit-exact rodam com a flag OFF (idxStore) — contrato exato intacto.

## Numeros (indice REAL, 1M x 768, Ryzen 7 5700X3D)
- float32: 12.07 Mvec/s (baseline L311) — 11.31 medido hoje no mesmo harness
- int8: 80.82 Mvec/s (100k, cache L3) e 48.63 Mvec/s (1M, RAM) = ~4x
- recall@1 = 1.0000, recall@5 = 0.9960, recall@10 = 0.8840, max score err
  0.0117 (dataset gaussiano L2-normalizado, 50 queries = row+ruido 0.05)
- O top-1 (vizinho real) e SEMPRE preservado; o recall@10 paga ~12% nos
  quase-empates (ranks 2-10 com gap ~0.01 = ordem do erro de quantizacao).

## Licoes
1. Benchmark de dataset grande: esquentar paginas (L340) — 2x deu 15M, 5x 52M.
2. Int8 tem recall 88% em quase-empates; quem precisa de exatidao total usa
   a flag OFF (float32) ou int16 (2 bytes/elem, ~26M vec/s teorico, erro
   256x menor) — kernel VPMADDWD i16 ja validado (sem bugs do assembler).
3. Contrato publico: Search() com int8 ON devolve scores aproximados —
   documentado em SQLiteVecConfig.DisableInt8; consumidores com tolerancia
   exata (1e-6) devem desligar a flag (TestSQLiteVec_StoreNormalized).
