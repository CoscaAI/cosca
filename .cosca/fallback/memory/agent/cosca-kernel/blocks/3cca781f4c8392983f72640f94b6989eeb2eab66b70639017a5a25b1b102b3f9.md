## O que foi medido
Instrumentacao da campanha (nao micro-otimizacao):

## Resultado (o que muda a campanha)
- 400/400 queries = FULL-SCAN do indice int8 (fast path atingido SEMPRE).
- scanned = 13.801 vetores/query (== TotalVectors) — NAO 1M, NAO 62k.
- latency media 1.02ms / p95 615us — o scan ja roda em regime cache (13.8k x
  768 = 10.6MB int8 < L3 96MB).
- Caminho hibrido bounded (CandidateIDs + CandidatePool 250) NUNCA usado:
  o knowledge.Search chama e.search.Search com CandidateIDs nil — o
  LayeredSearch (que seta os candidatos) nao e o caminho do `cosca knowledge
  search`. Capacidade LATENTE, nao caminho de producao.

## Decisao da campanha (epistemologia)
O problema de HOJE nao e o kernel (13.8k vetores em ~600us) — e o que esta
ANTES/DEPOIS (FTS + embedding + materializacao + ranking). O kernel int8 ja
opera no regime certo. Proximas fases: joelho V-Cache (FASE 3), recall real
(FASE 8), int16 (FASE 7) — para QUALIDADE e CRESCIMENTO, nao para o scan atual.
