| **Learned** | 1) O validador usa regex `^#[a-z][a-z0-9-]*$` — tags inválidas incluem uppercase (F7, R17, gRPC), números sozinhos (1 a 7), e kebab começando com dígito (24-agentes). 2) Numerais no início exigem decisão: manter número no fim (`#agentes-24`, `#providers-10`) ou por extenso (`#tres-ondas`, `#cinco-ondas`, `#seis-fases-completas`) — escolher por extenso para quantidades ordinais/contagem e número-no-fim para entidades técnicas. 3) A tag bruta "F7.4" (ponto) foi normalizada para `#f7-4` (ponto → hífen + minúsculas) em 18 entradas do cosca-devops. 4) Acrônimos → minúsculas simples: gRPC→`#grpc`, XSS→`#xss`, SSE→`#sse`, WebSocket→`#websocket`. 5) CRÍTICO: o validador varre o arquivo INTEIRO (seção b), não só a linha de Tags — menções em prosa como "Task 1" com cardinal ou "SLOs 2" também são sinalizadas como tags inválidas. Tags só devem ser corrigidas nas linhas `**Tags**`; prosa não é tag e não deve ser alterada (restam 6 falsos positivos de prosa: numerais 1 a 5 e 7). |
| **What worked well** | Classificar cada ocorrência antes de substituir (linha de Tags vs prosa) via grep com contexto. Regra de decisão por tipo: fase → f+número; número-no-início → número-no-fim ou por extenso; acrônimo → minúsculas. Verificação pós-fix com o próprio validador. |
| **What was difficult** | Numerais sozinhos (1 a 7) aparecem 39× no total, mas 100% deles estão em prosa/headings ("Task 1", "SLOs 2"), não em linhas de Tags — não é possível corrigi-los sem alterar texto de aprendizados. Discrepância contagem do relatório (F7 17×) vs validador (18×) porque o regex corta em "." e cada "F7.4" com hash vira o token "F7" sem o ".4". |
| **Improvement points** | 1) O validador deveria extrair tags apenas da linha `**Tags**` (seção b), eliminando 6 falsos positivos de prosa. 2) Documentar a regra de padronização numérica (por extenso vs número-no-fim) na LEARNING_PROTOCOL.md. |
