### 2026-07-30 — F2.3 Federation Engine design (publish/subscribe cross-project)

**Técnica**: Design de engine de federação de conhecimento cross-project com modelo publish/subscribe, MEMORY_GLOBAL em `~/.config/cosca/global-knowledge/`, e publicação restrita a princípios compilados pelo F9.1.

**Domínio**: architecture, federation, cross-project, knowledge-transfer, semantic-memory

**Contexto**: Criação da F2.3 Cross-project Knowledge Transfer como engine operacional leve, complementar à spec completa do Knowledge Federation Engine (cosca-semantic-memory). O Don especificou: apenas F9.1 compilado pode ser global, Don controla publish (nada automático), consulta global < 200ms.

**Aprendizados**:

1. **Separação portão vs transporte é o insight arquitetural chave**: Existem DOIS arquivos de federação — `knowledge-federation/SKILL.md` (spec completa: Hub, assinaturas KSIG, dedup, embeddings) e o novo `federation/SKILL.md` (camada operacional mínima). A regra de coexistência: este engine é o PORTÃO que decide O QUE sai do projeto; o outro é o TRANSPORTE que distribui. Nada entra no Hub sem passar pelo portão.

2. **"Apenas F9.1 compilado pode ser global" é uma restrição de segurança poderosa**: Ao restringir o store global a princípios compilados (maturity ≥ 0.7, freshness > 0.5, validação cross-agent), a federação herda toda a qualidade do pipeline de compilação. Learnings brutos são ruidosos demais para propagar entre projetos — a compilação é o filtro anti-poluição.

3. **Don-controlled publishing é mais que uma regra — é design**: Nenhum gatilho automático (post-commit, Stage 7, scheduler) pode publicar. A tag `#global-ready` só pode ser escrita pelo Don. Isso significa que a federação é PASSIVA por design — o engine espera, não empurra. A confiança cross-project depende desse controle humano.

4. **Local-first com fallback é o padrão de performance**: Consulta global SÓ dispara quando a busca local retorna relevance < threshold (default 0.50). Isso garante o orçamento de < 200ms de overhead sem dobrar latência em tasks com memória local rica. Cache de embeddings (LRU 1000, TTL 300s) é essencial.

5. **Atribuição obrigatória é inegociável**: Todo resultado global traz "aprendido em {project} por {agent}" + validated_in. Sem atribuição não há federação — há plágio de conhecimento. A proveniência (provenance.jsonl append-only) é o contrato de confiança entre projetos.

6. **Store global é project-agnostic e NUNCA versionado no projeto**: `~/.config/cosca/global-knowledge/` fica fora do git de qualquer projeto. O config.yaml de `~/.config/cosca/` (que já existe com paths/namespaces) é a base natural — a engine apenas adiciona o subdiretório `global-knowledge/`.

7. **Publish é barato e assíncrono (< 500ms)**: Copy + index + provenance append. Não bloqueia task. O custo real está na consulta — por isso o investimento em cache e índice FTS5.

8. **Exemplo do dead code removal valida o pipeline completo**: O princípio que já tinha maturity 0.759 no F9.1 (5 learnings, 3 agentes) é o exemplo perfeito de global-ready: compilado, validado, acionável. O fluxo cosca-test → publish → cosca-web → aplicar → validated_in += 1 mostra a retroalimentação que alimenta a Cognitive Gravity (F2.4, +20 cross_project_count).
