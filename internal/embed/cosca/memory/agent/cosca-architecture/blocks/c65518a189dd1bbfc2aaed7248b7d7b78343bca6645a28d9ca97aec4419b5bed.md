### 2026-07-30 — F9.6 Cognitive Time Machine Engine design

**Técnica**: Design do Cognitive Time Machine Engine — reconstrução de estado cognitivo em qualquer data passada
**Domínio**: architecture, time-travel, cognitive-snapshots, temporal-analysis
**Contexto**: Criação do F9.6 como engine de "fotografia cognitiva" que permite revisitar decisões com contexto completo da época. Complementa o F7.5 Decision Replay.

**Aprendizados**:

1. **Snapshot cognitivo como unidade fundamental**: O conceito de snapshot (10 dimensões: agentes, conhecimento, engines, qualidade, trust, CMI, etc.) resolve o problema de "como saber o que o Cosca sabia na data X". Cada snapshot é um YAML que captura o estado completo — de learnings a CMI.

2. **Pipeline de 4 etapas com fallback**: A reconstrução tem 4 passos (resolver data → carregar snapshot ou reconstruir → apresentar → comparar). O fallback entre snapshot automático (rápido) e reconstrução via git (completo) garante performance sem perder fidelidade histórica.

3. **Time Machine + Decision Replay = contexto completo**: A integração com F7.5 é o insight arquitetural mais importante. Juntos, resolvem o viés de hindsight: o replay mostra a decisão com as fontes da época (Trust Registry vazio, zero DDNAs, 19 learnings), não com o conhecimento de hoje.

4. **Score 2.4 → 10.0 em 2 dias**: O exemplo real com dados de 28/jul vs 30/jul demonstra que o Time Machine não é teórico — ele captura uma evolução real de +317%. O diff por dimensão mostra exatamente onde o sistema evoluiu.

5. **Snapshot automático via memorize-commit é essencial**: Sem snapshots automáticos, cada reconstrução precisaria de git checkout + coleta de fontes, que é mais lenta e menos confiável. Com snapshots a cada commit, a reconstrução é O(1) — apenas carregar YAML.

6. **Proteções de segurança no git checkout**: O time machine precisa alterar o working directory via git. As proteções (verificar dirty files, restaurar ao final, abortar com instruções claras) são essenciais para não perder trabalho do Don.

7. **ENGINEERING_TIMELINE como espinha dorsal**: A timeline existente ganha um novo campo (cognitive_snapshot_hash) que conecta cada evento da timeline ao snapshot correspondente. Isso transforma a timeline de um "registro de eventos" em um "índice temporal navegável".

8. **Formato de diff com destaques e pontos de atenção**: O diff temporal não mostra apenas números — ele destaca os maiores avanços (🔥) e os pontos de atenção (⚠️). Isso transforma dados brutos em narrativa de evolução.
