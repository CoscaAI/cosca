### 2026-07-30 — F7.3 Engineering Score por Commit design

**Técnica**: Design de sistema de score técnico composto por commit com 6 dimensões, pesos derivados do Quality Gates existentes mas adaptados para granularidade por commit.

**Domínio**: analytics, architecture, quality-metrics, engineering-intelligence

**Contexto**: Implementação do F7.3 (Engineering Score por Commit) como parte da F7 Engineering Intelligence. O score alimenta o Trust Registry (F7.2) e o Prediction Engine (F7.1).

**Aprendizados**:

1. **Alinhamento com QUALITY_GATES.md mas não duplicação**: A fórmula do Engineering Score NOBLEIA a fórmula do Quality Gates (`OVERALL`) mas com pesos diferentes — Code Quality ganha peso (0.25 vs 0.20) porque commits são primeiro sobre código; Security perde peso (0.15 vs 0.25) porque a maioria dos commits não introduz superfícies de ataque; Testing ganha peso (0.20 vs 0.15) porque cada commit deve ser testado. Isso evita duplicação enquanto adapta a métrica para o contexto de commit individual.

2. **Dimensão Testing requer tratamento especial para commits de documentação**: Commits docs-only (como o expurgo 792c000) naturalmente têm testing ≈ 0.225. Em vez de penalizar, o scoring permite que docs-only commits atinjam 70-85 mesmo com testing baixo porque as outras dimensões compensam. Isso é correto — documentação não precisa de testes, mas o score reflete que é um commit de documentação.

3. **Seis dimensões ortogonais com overlap mínimo**: Architecture, Code Quality, Testing, Security, Performance, Documentation cobrem todos os eixos de qualidade sem sobreposição significativa. A cada dimensão com subcritérios específicos evita que um commit seja superavaliado por ser bom em apenas uma dimensão.

4. **Integração bidirecional com Trust Registry**: O score não só alimenta o Trust Registry (confidence_delta) como também é alimentado por ele — agentes com confiança alta tendem a ter scores ligeiramente mais altos (viés de calibragem). O dono (Don) pode fazer override manual.

5. **Exemplo real validou a fórmula**: O commit 792c000 (expurgo de infraestrutura fictícia) scoreou 79.5 (Bom) — esperado para um commit de documentação/deleção que não tem testes mas é arquiteturalmente correto e seguro. O breakdown mostra exatamente por quê: Code Quality 25.0 (perfeito), Testing 4.5 (baixo), Architecture 18.5 (bom).

6. **Pipeline < 1s é viável**: git diff + análise string-based + fórmula matemática = execução em < 1s para a vasta maioria dos commits. Commits excepcionalmente grandes (+5000 LOC) podem levar até 2s, mas são raros.
