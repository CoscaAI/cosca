### 2026-07-30 — F10.4 Organizational Memory Engine design

**Técnica**: Design de engine de memória organizacional — captura padrões de processo e colaboração entre agentes (quem funciona com quem), distinto de conhecimento técnico (F9.1) e reputação individual (F7.2).

**Domínio**: architecture, organizational-memory, collaboration-patterns, process-dna, multi-agent

**Contexto**: Criação da F10.4 como último engine da Fase 10 (depois de F10.1 Cognitive Economics), especificado pelo Don no next-evolution-phases.md: "Organizational Memory — padrões organizacionais: 'Toda vez que arquitetura e frontend trabalham separados, conflitos aumentam.'" com engine `org-memory/SKILL.md` + correlação de eventos, prioridade P2, critério de sucesso "identifica 1 padrão organizacional com confiança ≥ 0.70".

**Aprendizados**:

1. **F10.4 é a terceira camada de memória — o padrão relacional**: F7.2 Trust Registry é memória individual (reputação), F9.1 Experience Compiler é memória semântica (técnico), F10.4 é memória relacional (quem funciona com quem). A tabela de diferenciação (unidade = relações entre agentes) é o que evita duplicação com as engines vizinhas. A pergunta central "quem funciona bem COM quem?" não é respondida por nenhuma outra engine.

2. **Cinco dimensões com exemplo do Don preservado**: Colaboração (pares), Sequência (ordem), Conflito (mesmo arquivo), Timing (paralelo vs sequencial), Composição (mix por task type). Os exemplos do Don ("cosca-testing + cosca-backend juntos = 95% sucesso", "arquitetura decide sozinho → frontend refaz 3x", "tasks paralelas em pacotes diferentes = +40% velocidade") foram incorporados literalmente como padrões de referência de cada dimensão.

3. **Fórmula do Don com componente derivado crítico**: A fórmula `occurrences×0.4 + consistency×0.3 + data_quality×0.2 + recency×0.1` foi mantida literalmente, mas o design precisou definir: normalização `min(N/10, 1.0)` para occurrences, consistency como fração na direção dominante, data_quality como média de 3 sub-fatores (completude, corroboração cross-source, granularidade) e recency com meia-vida de 90 dias. A normalização de occurrences cria uma propriedade elegante: com N=3 (mínimo), o teto é 0.72 — só passa com TUDO perfeito. Isso implementa a regra "3+ ocorrências" com rigor em vez de atalho.

4. **Correlação ≠ causalidade é o princípio de governança mais importante**: O engine detecta regularidades, não causas. Toda recomendação é condicional ("quando X ocorre, tende a Y"). Recomendações NÃO são regras — o Don aprova. O ciclo de vida em 6 regras (G1-G6) com "revisit 90 dias" espelha o padrão do F9.2/DECISION_DNA (tudo revisitável, nada permanente).

5. **Integração F8.1 via coeficiente de sinergia é a ponte mais elegante**: Padrões de colaboração viram `synergy(A,B) ∈ [-1,1]` que o Capability Market aplica como multiplicador `(1 + synergy)` em leilões multi-agente. Pares conflituosos (synergy < -0.30) não são co-alocados. O Market retroalimenta a F10.4 com resultados de alocação — ciclo virtuoso de dados.

6. **DDNA de processo é a materialização da recomendação aprovada**: Diferente de DDNA de decisão técnica, o DDNA de processo descreve uma regra sobre o PROCESSO (ex: "revisão conjunta obrigatória antes de decisões de API"), com `process_rule: true` e `org_pattern_ref` linkando ao padrão que a originou. Isso dá rastreabilidade total: regra → padrão → ocorrências → decisão do Don.

7. **Exemplo validado matematicamente**: O exemplo do Don (5 sprints, confiança 0.78) foi reproduzido: occurrences 5→0.50×0.4=0.20 + consistency 1.0×0.3=0.30 + data_quality 0.90×0.2=0.18 + recency 1.0×0.1=0.10 = 0.78 ✓. Os padrões secundários do mesmo ciclo demonstram a escala de confiança: 0.77 (recomendado), 0.75 (recomendado), 0.615 (emergente, não recomendado).

8. **Pipeline < 5s viável com dados existentes**: Trust Registry (YAML parseável) + Timeline (tabelas) + git log --name-only + CSVs B1-B5 = ~1.8s. O engine NÃO cria dados novos — re-agrega os existentes. Mesmo padrão dos engines F10.x: coleta leve sobre fontes já mantidas.

9. **Anti-padrão evitado — não atribuir culpa**: O padrão "arquitetura decide sozinho → frontend refaz 3x" descreve um processo disfuncional, não julga o agente. A regra G6 (sem atribuição de culpa) protege o sistema de vieses de reputação que contaminariam o Trust Registry.

10. **Referências cruzadas com DDNA e Market exigem precisão de paths**: DECISION_DNA_FORMAT.md fica em `memory/`, TRUST_REGISTRY.md em `memory/trust/`, ENGINEERING_TIMELINE.md em `memory/timeline/` — paths relativos a partir de `engines/org-memory/` usam `../../`. Toda referência foi validada contra o filesystem real.
