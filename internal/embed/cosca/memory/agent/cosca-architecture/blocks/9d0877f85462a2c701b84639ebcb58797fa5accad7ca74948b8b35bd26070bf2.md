### 2026-07-30 — F2.4 Cognitive Gravity Engine v2 design (redesign completo)

**Técnica**: Redesign do Cognitive Gravity Engine de v1.0.0 (modelo de gravidade por entrada de conhecimento, Memory Chief) para v2.0.0 (modelo canônico do Don: atração de conhecimento afim por domínio). Preservação do v1.0.0 como micro-modelo complementar em GRAVITY_ENTRY.md.

**Domínio**: architecture, cognitive-gravity, knowledge-attraction, domain-modeling, context-injection

**Contexto**: Don especificou a F2.4 como sistema de atração de conhecimento afim — "assim como a gravidade atrai massa, o Cognitive Gravity atrai learnings/patterns/DDNA relacionados quando um agente trabalha num domínio". Fórmula literal: `gravity_force(domínio, task) = knowledge_mass(X) × proximity(X, task)`, com `knowledge_mass = learnings + patterns×2 + ddna×3` e `proximity = semantic_similarity(tags) + recency_factor`. Pipeline de 5 passos com injeção de top-3 domínios × 3 itens. Órbitas alimentando F1.4. Integrações F9.1/F1.6/F1.3.

**Aprendizados**:

1. **O v1.0.0 não estava errado — estava em outra escala**: O modelo do Memory Chief (validation_count, diversity, cross_project, time_factor, evidence_strength, níveis Dust→Planet) mede a influência de UMA entrada de conhecimento. O modelo do Don mede a atração entre DOMÍNIOS e a task atual. São complementares: o micro-modelo (v1.0.0) ordena o que o macro-modelo (v2.0.0) atraiu. A preservação em GRAVITY_ENTRY.md com integração opcional (`entry_level_weight: 0.3`) é o padrão de coexistência correto — nunca apagar trabalho anterior válido, reposicioná-lo.

2. **A ponderação da massa é densidade, não hierarquia**: learnings ×1, patterns ×2, ddna ×3 refletem a densidade de conhecimento — 1 DDNA (decisão documentada com riscos/resultado) vale 3 learnings brutos. Compilação (F9.1) transforma N learnings em 1 pattern: a massa pode subir mesmo com volume caindo, porque o padrão compilado vale mais. Isso conecta F2.4 a F9.1 de forma natural.

3. **Proximidade é o fator de delicadeza da fórmula**: `semantic_similarity (0-0.8) + recency_factor (0-0.2)` limita o viés de recência a 20% — conhecimento novo não validado não domina a atração, mas conhecimento fresco do domínio aproxima a task. A separação entre similaridade (Semantic Memory) e recência (F1.4 freshness) mantém cada fonte de proximidade com dono claro.

4. **Entropia como multiplicador de redução é o insight arquitetural**: `gravity_force_final = massa × proximidade × (1 − entropy_penalty)` — a entropia atual 0.433 corta a gravidade em 43%. A justificativa é forte: injetar conhecimento contraditório/stale é pior que não injetar. Isso cria o ciclo virtuoso com F9.4 (deprecar stale → entropia cai → gravidade sobe).

5. **Órbitas são a interface entre atração e envelhecimento**: `orbit_radius = 1 − freshness` — o que esfria (F1.4) migra para a órbita externa e deixa de ser atraído; o que deixa de ser atraído esfria mais rápido. A órbita externa alimenta Wisdom Decay/revalidação naturalmente, sem engine extra.

6. **Limite de 9 itens (3×3) é uma restrição de contexto, não de custo**: O overhead de injeção é < 50ms (cache de massa TTL 300s + 1 query vetorial). O limite existe porque contexto é recurso finito — 9 learnings bem escolhidos valem mais que 30. Don control absoluto via `cosca gravity off`.

7. **O exemplo do Don mapeia para learnings reais**: L9 (Parallel CI Fix, race), L21 (Coverage Audit, 20 races), L29 (Onda F0, 21 races) — todos sobre races no cosca-kernel. O exemplo da task "corrigir race condition no registry" injeta exatamente L9+L21+L29, validando que a fórmula funciona com dados reais do repositório.

8. **Referências quebradas se curam no redesign**: O workflow cognitive-maturity-implementation.md e o knowledge-federation/SKILL.md apontavam para `GRAVITY.md` (arquivo que nunca existiu). O redesign consolidou tudo para `SKILL.md` (17 referências) e atualizou owner (Memory Chief → Architecture Chief). Verificar referências de arquivos é parte obrigatória de qualquer redesign.
