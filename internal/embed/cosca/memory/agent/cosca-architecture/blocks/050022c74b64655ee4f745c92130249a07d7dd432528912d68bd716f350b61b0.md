### 2026-07-30 — F2.6 Pattern Evolution Engine v2 design (redesign completo)

**Técnica**: Redesign do Pattern Evolution Engine de v1.0.0 (6 estados, Memory Chief) para v2.0.0 (5 estados com tags, fórmula de maturidade, pipeline semanal < 5s) por ordem do Don
**Domínio**: architecture, pattern-evolution, knowledge-lifecycle, evolutionary-systems
**Contexto**: Don especificou a estrutura exata da F2.6: definição (padrões como seres vivos), ciclo de vida NASCIMENTO→CANDIDATO→MADURO→PRINCÍPIO→MORTE, fórmula pattern_evolution_score, pipeline semanal < 5s, integração com F9.1 e F1.4, exemplo com same-package-access (L22)

**Aprendizados**:

1. **Padrões são seres vivos, não documentos**: A mudança de paradigma central do v2 — padrão nasce num learning, vira candidato na 3ª ocorrência, maduro com 3+ usos, princípio com 10+ usos, e morre quando obsoleto. A metáfora biológica (ecossistema, fóssil, pattern_history) comunica o ciclo de vida inteiro de forma intuitiva para o Don.

2. **Tag de lifecycle no patterns.md é o contrato observável**: As tags `#candidate`, `#validated`, `#principle`, `#stale` são o que torna o sistema operável — qualquer agente lê o estado do padrão no cabeçalho sem consultar YAML. A tag é o "pulse" do ser vivo.

3. **Fórmula do Don é ouro — não reinventar**: A fórmula especificada (uso 0.5 + idade 0.2 + cross-agent 0.2 + review 0.1, com caps 10 usos/90 dias/5 agentes) foi mantida literalmente. O trabalho de design foi definir os componentes derivados (cross_agent_uses, review_score) e os thresholds de classificação (0.2 moribundo, 0.4 validated, 0.7 maduro), não substituir a intenção do Don.

4. **F2.6 ≠ F9.1 — duas fórmulas, duas perguntas**: A distinção crítica contra duplicação: F2.6 mede saúde do padrão como ser vivo (uso, idade, cross-agent, revisão); F9.1 mede maturidade de compilação (learnings, freshness, impacto). F2.6 NUNCA promove a princípio — ele notifica (evento pattern.mature) e alimenta o F9.1, que decide; o Don aprova. Separação de concerns preservada.

5. **Integração com F1.4 define a morte**: "Padrões não usados há 90 dias → decay → reavaliação" é o mecanismo de morte mais importante. O fluxo 60d (warning) → 90d (#stale + reavaliação) → reavaliação (ressuscitar OU morrer) → pattern_history dá escalação progressiva que previne morte acidental.

6. **Pattern history NUNCA exclui**: O protocolo de morte preserva o YAML integral com trilha de evolução em pattern_history/ — consistente com o padrão do F9.4 (learning_history). A regra "morto não é excluído" é constitucional no Cosca.

7. **Pipeline semanal em 6 passos < 5s é viável**: Varredura de 54 patterns.md (~1.5s) + contagem de usos via índice FTS5 (~1.5s) + aritmética (~0.1s) + classificação/movimentação (~1.5s) = < 5s. O segredo: contagem de usos usa tags indexadas, não leitura completa de learnings.md.

8. **Exemplo real valida o ciclo completo**: O same-package-access (L22) nasceu com 3 packages no mesmo learning (3ª ocorrência = 3 packages), foi validado por agentes de testing independentes (openaicompat, embeddings), e projeta score 0.867 com 12 usos → princípio via F9.1. O exemplo cobre nascimento, maturidade, promoção e morte (projeção) — demonstrando todos os estados do ciclo.

9. **Compatibilidade retroativa com v1.0.0**: O mapeamento dos 6 estados antigos (PROPOSED/DRAFT/STABLE/DEPRECATED/SUPERSEDED/RETIRED) para os 5 novos garante que patterns.md existentes não quebram durante a migração. A transição é gradual — YAML canônico por padrão ativo, patterns.md tolerante a formatos heterogêneos.

10. **Coexistência com 54 patterns.md**: A engine assume que patterns.md são visões derivadas (human-readable) e o YAML é a fonte canônica — mas o pipeline lê ambos para tolerar agentes que ainda não migraram. Normalização em memória antes do cálculo.
