### 2026-07-30 — F1.6 Cognitive Entropy Engine design

**Técnica**: Design de engine de medição de desorganização do conhecimento com fórmula de 3 componentes (contradictions×3, stale×2, gaps×1), normalizada por total_knowledge. Pipeline semanal com alertas automáticos e integração com F2.1 Cognitive Economy.

**Domínio**: architecture, cognitive-metrics, knowledge-health, entropy

**Contexto**: Implementação do F1.6 como engine operacional de Cognitive Entropy, complementar ao dashboard de analytics (5 componentes, 0-100%). Diferenciar engine (3 componentes, 0.0-1.0, alerta semanal) de dashboard (5 componentes, 0-100%, auditoria mensal).

**Aprendizados**:

1. **Três componentes com pesos diferentes refletem dano real**: Contradições (peso 3) são dano ativo — agentes tomam decisões opostas. Stale (peso 2) é dano silencioso — conhecimento vencido engana quem confia. Gaps (peso 1) são dano potencial — sabemos que existem e monitoramos. A ponderação não é arbitrária: reflete o custo real de cada tipo de desorganização nas decisões dos agentes.

2. **Fórmula simplificada vs dashboard de analytics**: O analytics já tinha uma métrica de entropia com 5 componentes (Contradiction, Staleness, Fragmentation, Orphan, Consolidation) em escala 0-100%. O engine precisava de algo mais operacional — 3 componentes, 0.0-1.0, que pudesse alimentar diretamente a Cognitive Economy (F2.1) como qualificador de risco. A escolha foi deliberada: simplicidade para integração, não concorrência com o dashboard.

3. **A normalização por total_knowledge é essencial**: Sem ela, uma base pequena com poucas contradições pareceria mais organizada que uma base grande com algumas contradições. A divisão por total_knowledge torna o score comparável entre diferentes tamanhos de base.

4. **Entropia atual 0.433 (🔴 alta) — dominada por gaps sem DDNA (57.1%)**: 4 gaps sem DDNA contribuem mais que a única contradição ativa. Isso é típico de sistema em construção: conhecimento recente (zero stale), mas rastreabilidade incompleta (gaps). A prioridade imediata é criar DDNAs para os 4 gaps.

5. **Integração com F2.1 foi o design mais desafiador**: A entropia entra como `risk_penalty = entropy × knowledge_dependency_factor` no efficiency score. O fator de dependência (0.0-1.0) permite que ações independentes de conhecimento (ex: `go build`) não sejam penalizadas, enquanto ações críticas (ex: decisão arquitetural baseada em learnings) sofrem penalidade proporcional. O ajuste fino desse fator requer calibração com dados reais.

6. **Thresholds precisam de validação empírica**: Os thresholds (🟢<0.10, 🟡0.10-0.25, 🔴>0.25) são baseados em raciocínio teórico. Com uma base de 30 learnings, 1 contradição já leva a 0.100 (limiar 🟢→🟡) e 3 contradições a 0.300 (🔴). Pode ser que 1 contradição em 30 seja aceitável — precisamos de dados históricos para calibrar.

7. **Pipeline semanal com coleta de F1.3 e F1.4**: O engine não recalcula entropia a partir do zero — ele consome dados já processados pelo Wisdom Decay (contradictions, stale) e Gap Detection (gaps sem DDNA). O custo adicional é mínimo (< 1.5s) porque o trabalho pesado já foi feito pelas engines dependentes.
