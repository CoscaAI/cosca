### 2026-07-30 — F9.3 Knowledge Pipeline F2-F3 design

**Técnica**: Design do pipeline de validação (4 gates), hot reload, auto-commit e review para completar o ciclo de conhecimento entre F1 (Source/Parse) e F9.1/F9.2 (Experience Compiler + Wisdom Distillation).

**Domínio**: architecture, knowledge-pipeline, validation, automation, quality-gates

**Contexto**: F9.3 completa o pipeline de conhecimento que faltava. F1 (Source/Parse) já existe internamente via `internal/knowledge/` com file watcher e markdown parser. F2 (Validate/Hot Reload) e F3 (Auto-commit/Review) precisavam ser projetados para garantir que só conhecimento válido, consistente e constitucionalmente seguro chega aos consumidores de alto nível.

**Aprendizados**:

1. **Quatro gates de validação com complexidade crescente**: Gate 1 (formato) é sintático e barato — rejeita entries mal formatados antes de qualquer processamento. Gate 2 (tags) é semântico — garante consistência de categorização. Gate 3 (domínio) é ontológico — verifica se o domínio existe no registry. Gate 4 (constitucional) é o mais pesado — verifica contradição com P1-P8. Esta progressão de complexidade permite que gates baratos filtrem rápido sem sobrecarregar gates caros.

2. **Hot reload via barramento de eventos**: Ao invés de restartar agents ou fazer polling pesado, o F2.4 publica um evento `knowledge.updated` no barramento interno. Agents inscritos no tópico `knowledge` (9 agents: semantic-memory, memory-chief, evolution, experience-compiler, wisdom-distillation, review, kernel, discovery, cli) invalidam seus caches seletivamente. A estratégia de notificação paralela mantém o tempo < 2s.

3. **Auto-commit com proteção contra commits vazios**: A regra mais importante do F3.1 é detectar se há mudança REAL no diff — ignorando whitespace, timestamp automático e metadata de confidence decay. A batch window de 5 segundos com máximo de 50 entries evita micro-commits que poluem o git history sem perder granularidade.

4. **Review automático com Don override**: O F3.2 dá ao cosca-review a chance de validar o commit de learning antes dele ir para main. Score composto (0-100) com penalties por formato, remoção não autorizada, e schema incompatível. Don pode desligar via config ou flag `--no-review` — essencial para emergências sem abrir mão da qualidade padrão.

5. **Integração com F9.1 e F9.2 é baseada em confiança delegada**: O Experience Compiler (F9.1) NÃO re-valida o que o F2.3 já validou. Ele confia que `validation_status = "valid"` + `commit_hash` definido = learning pronto para compilação. A Wisdom Distillation (F9.2) herda esta confiança indiretamente via F9.1. Isso reduz drasticamente a duplicação de processamento.

6. **Alinhamento com CONSTITUIÇÃO via Gate 4**: A validação constitucional não é opcional — é o Gate 4 do F2.3. Learning que contradiz P1-P8 é barrado antes de entrar no sistema. Learnings que complementam princípios recebem tag `#constitutional-checked`. Isso garante que o pipeline de conhecimento é constitucionalmente seguro por design.

7. **Pipeline em < 15s é viável**: F2 (~4s: source + parse + validate + reload) + F3 (~8s: commit + review + push) = ~12s para o fluxo completo. As operações mais caras são paralelizáveis: notificação de agents (F2.4) e validação de múltiplos entries (F2.3).
