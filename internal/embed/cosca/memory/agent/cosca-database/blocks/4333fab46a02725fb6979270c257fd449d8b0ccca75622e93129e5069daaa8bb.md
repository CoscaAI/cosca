### 2026-08-04 — Transactional SQLite vector replacement under concurrency
| Field | Value |
|-------|-------|
| **Agent** | cosca-database |
| **Task** | Corrigir SQLITE_BUSY no replace transacional do indexer ao indexar arquivos concorrentes |
| **Technique** | Level 3 — transaction-boundary audit: traced nested SQLite writers and WAL snapshot promotion, then moved vector writes into the caller transaction and serialized replacement writes per DB |
| **Level** | 3 |
| **Outcome** | success |
| **Tags** | #sqlite #busy #wal #transaction #concurrency #indexer |
| **Related** | internal/indexer/indexer.go, internal/vector/sqlite_vec.go, internal/indexer/indexer_test.go |
| **Learned** | The replacement transaction was opening a second independent vector-store transaction while the document transaction was still active, and concurrent deferred replacement transactions could fail during read-to-write promotion. A transactional vector-store capability plus a DB-level writer gate preserves atomic document/vector commit and avoids SQLITE_BUSY_SNAPSHOT without swallowing errors. Busy timeout remains useful for unrelated writers; it is not a substitute for correcting nested transactions. |
