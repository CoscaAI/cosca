| **Learned** | **(1) O Fabric.Health() retorna string ("healthy"/"degraded") mas runtime.Subsystem exige Health() ComponentStatus** — o `go build` falhou na primeira tentativa (`wrong type for method Health`). A auditoria inicial afirmava que o Fabric já satisfazia o contrato; era falso. Solução: adaptador `computeSubsystem` no ponto de integração (padrão ProviderAdapter do repo) com compile-time check `var _ rt.Subsystem = (*computeSubsystem)(nil)`. Alternativa (rejeitada): refatorar compute.Fabric.Health() exigiria import runtime dentro de compute (ciclo? não, mas reescrever ~98% dos testes) — o adaptador mantém o compute package autossuficiente. **(2) Hooks initCompute/startCompute/stopCompute já existiam no lifecycle (linhas 155/182/209) mas começam com `if r.compute == nil { return nil }`** — sem RegisterCompute, o fabric nunca nascia e o health check reportava o componente sem nunca tê-lo iniciado. O padrão de "código testado até o talo, morto em produção por falta de 1 linha de wiring" se repete (ChatRegistry G0a teve o mesmo diagnóstico). **(3) Smoke test real**: binário compilado, `COSCA_JAILED=1` + `COSCA_DEV_MODE=true` para escapar do bwrap (user namespaces bloqueados no ambiente), login admin/admin, GET /v1/status → components.compute-fabric = healthy. A prova viva > qualquer cobertura de teste. **(4) Dica de ambiente**: rodar o binário sem jaula exige `COSCA_JAILED=1`; endpoints autenticados exigem `COSCA_JWT_SECRET` setado (serve.go recusa boot sem ele). |
