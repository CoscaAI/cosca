| **Learned** | AS 10 DICAS DO PROFESSOR (após a Fase 1 validada): (1) NÃO deixar o Hardware Brain virar INVENTÁRIO — o objetivo é hardware→capacidade efetiva→hipóteses→experimentos→evidência→perfil de performance, não "CPU: AMD / RAM: 32GB". (2) SEPARAR FACT de MEASUREMENT de INFERENCE: FACT = o hardware declarou (CPU Ryzen, 8 cores, AVX2=true); MEASURED = o benchmark observou (12.6 Mvec/s, ~38 GB/s, 8 workers); INFERRED = o sistema concluiu (provável memory-bound). NUNCA misturar os três — isso deixa o brain confiável. (3) GUARDAR EXPERIMENTOS QUE PERDERAM com estrutura completa: Experiment/Norms, Workload 100K×768, Baseline 12.4, Resultado 10.6, Delta -14.5%, Confidence HIGH, Decision REJECTED, Reason "overhead de acesso supera benefício" — no futuro, outro agente que pensar "pré-calcular normas!" recebe "já testamos esta hipótese neste workload" — economiza tokens e tempo. (4) CONTRATO DE BENCHMARK FIXO para agentes: INPUT (dataset/workload/hardware/restrições) → EXPERIMENT (uma variável) → OUTPUT (latência/throughput/bandwidth/allocations/variance/confidence) → DECISION (KEEP/REJECT/INCONCLUSIVE) — o agente não inventa métricas diferentes a cada rodada. (5) GPU AINDA MAIS RIGOROSA: DISCOVERED→DRIVER_PRESENT→BACKEND_AVAILABLE→DEVICE_INITIALIZED→CAPABILITY_VERIFIED→WORKLOAD_VERIFIED→BENCHMARKED — nunca "lspci achou GPU = GPU disponível" (falsos positivos). (6) FINGERPRINT sem virar modelo fixo: hardware_fingerprint + workload_fingerprint + environment + benchmark_evidence = performance profile — o MESMO 5700X3D pode ter configs diferentes por workload. (7) APRENDIZADO LENTO: nenhum benchmark pode automaticamente alterar produção — benchmark→evidence→candidate→validation→profile, SÓ DEPOIS profile→runtime recommendation, e muito mais tarde recommendation→autotune. Evita que medição ruim piore o sistema. (8) MODO CONSERVADOR SEMPRE: "Performance optimization is optional. Correct execution is mandatory." Se o brain não souber→config segura; inconclusivo→config conhecida; GPU duvidosa→CPU fallback; memória limitada→reduzir paralelismo. O sistema NUNCA fica incapaz de executar por não conseguir otimizar. (9) NÃO PERSEGUIR O BANDWIDTH TEÓRICO (57.6 GB/s): o observado (~37-43 GB/s) é uma observação do WORKLOAD, não o limite físico da RAM. Separar: bandwidth teórico ≠ bandwidth medido por microbenchmark ≠ bandwidth efetivo do algoritmo (o algoritmo tem acesso/concorrência/layout/cache/sync/overhead próprios). Evita otimização placebo. (10) UMA FASE POR VEZ (a principal): CPU→Memory→Topology→Environment→Limits→GPU→Capability→Workload→Benchmark→Profile — quando o agente recebe um perímetro extremamente preciso, trabalha muito bem sozinho; não dar um continente inteiro de uma vez. BÔNUS (validação do método): a consolidação em 4 commits separados + assinatura + working tree limpo = proveniência limpa ("este commit foi quando o Cosca aprendeu a conhecer a própria CPU") — ponto de retorno estável para experimentar sem medo. |
