| **Learned** | **(1) Event sourcing é A fundação da execução durável — e o Cosca não tem.** Nosso workflow engine (L153) roda steps em memória: se o runtime cair, perde-se tudo. O Temporal prova que event sourcing com replay resolve: cada step gera HistoryEvent imutável, o estado é replay, a execução sobrevive a qualquer crash. **(2) A arquitetura de 4 serviços (Frontend/History/Matching/Worker) é a decomposição canônica de um motor de workflow.** Frontend = API gateway, History = event sourcing + state machine, Matching = buffer durável de tasks, Worker = background processing. Cada um escala independentemente. **(3) O pipeline staged execution (decisão → evento → task → side effect) é superior ao nosso modelo síncrono.** No Cosca, um step executa e bloqueia até terminar. No Temporal, a decisão só escreve eventos (rápido), e as tasks derivadas executam assincronamente. Isso permite paralelismo real entre steps independentes. **(4) Task Queue como buffer durável é o que falta no nosso Matching.** Hoje não temos fila de tasks entre planner e executor — as tasks são criadas em memória. O padrão SpoolTask (persistir) + getTasksPump (ler) + taskAckManager (rastrear entregas) garante exactly-once delivery. **(5) Optimistic concurrency com conditional updates (NextEventID + DBRecordVersion) é mais escalável que locks distribuídos.** O Temporal processa milhões de workflows sem locks — CAS no banco + dedup por RequestID + vector clock consistency. Nossas engines compartilhadas (L154) precisam disso. **(6) Shard com RangeID fencing é o modelo de scale-out horizontal.** Workflows hasheados para shards, RangeID como fencing token, ringpop para membership. Graceful degradation via Shard Linger evita dropping de trabalho durante rebalance. **(7) O checksum (CRC32 sobre mutable state) é uma ideia simples e poderosa para detectar divergência de estado.** Nosso Recovery Loop retry às cegas — se o estado diverge entre tentativas, não sabemos. Checksum + validação no reload fecha essa brecha. **(8) HSM (Hierarchical State Machine) é o contrato universal para componentes de workflow.** Cada agente Cosca poderia implementar StateMachineDefinition + TaskSerializer + Executor, e o motor de workflow os invocaria automaticamente. O StateMachineRef com versioned transitions resolve staleness detection. **(9) Dynamic configuration com constraint precedence é superior ao config.yaml estático.** Poder ajustar timeouts, limites de rate, e parâmetros de agentes em runtime, com escopo por namespace/taskqueue, é essencial para operação. **(10) Timer como task persistida, não goroutine, é o jeito certo de fazer timeout durável.** Nosso workflow engine não tem timeouts que sobrevivam a restart — UserTimerTask com VisibilityTimestamp resolve. |
