| **Learned** | **(1) O modelo de segurança certo para TUI é o do OpenCode: o processo INTERATIVO roda livre (UX), a EXECUÇÃO de comandos emitidos pelo LLM é sandboxada por-comando. A jaula é para daemons (expostos, sem supervisão), não para ferramentas interativas.** **(2) O terminal NÃO precisa do runtime daemon — apenas um health check opcional de 2s ("Runtime: unavailable (limited functionality)" como fallback); chat providers, pipeline, workflows e knowledge são todos locais.** **(3) A jaula prejudicava a UX: debug noise, TTY/cores/rede restritos, lentidão (reexec + bwrap por comando). O sandbox por-comando (internal/chat/sandbox/gate.go, sandbox.NewGate → bwrap por execução) JÁ EXISTIA mas só estava ligado no cosca-chat, não no terminal.** **(4) A discussão de trade-off de segurança com o Don: a jaula protege o PROCESSO do terminal de ler /home; o sandbox por-comando protege a EXECUÇÃO de tools (a parte perigosa — comandos arbitrários do LLM). Decisão: o processo do terminal é código confiável (nosso); a execução de tools é o risco → sandboxed por-comando.** **(5) O memfd (binário em RAM) é ortogonal à jaula — remover a jaula NÃO remove a proteção em RAM.** **(6) Debug noise num TUI é bug de UX: nível de log default deve ser info/warn; debug é opt-in via env.** **(7) O instinto do Don estava correto e foi validado pelo próprio OpenCode rodando o agente cosca-kernel perfeitamente fora de qualquer jaula.** |
