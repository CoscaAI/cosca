# L344 — Analise da resposta do professor ao relatorio de performance

## Contexto
O professor leu o relatorio do fast path int8 (docs/reports/performance-int8-
fastpath) e devolveu uma analise extensa: validou a metodologia e apontou
lacunas. O chef pediu para analisar essa conversa.

## O que o professor validou (e por que importa)
- "Relatorio de engenharia de verdade": o valor NAO e o 52.66 Mvec/s, e a
  cadeia de evidencia que justifica onde funciona, onde para e qual o proximo
  gargalo.
- Elogiou: matar hipotese errada antes de otimizar (bandwidth, nao CPU),
  mudar a representacao (4x menos dados > 4x mais rapido), observacao sobre
  narrativa (5 kernels errados ate a execucao contradizer os bytes), medir o
  preco (recall), V-Cache como 2a mudanca de regime, fallback defensivo.

## As correcoes dele (o que NAO deixou passar)
1. "Nao e possivel subir mais sem trocar RAM" esta ERRADA como universal:
   correto e "nao e possivel subir significativamente NESTE regime mantendo
   o mesmo algoritmo/representacao/contrato". Existem int16, tiling, layout,
   filtros, ANN, GPU. Limite fisico = para aquele caminho, nao o problema.
2. Nao promover a FACT ainda: "int8 seguro pro RAG" (so 50 queries
   sinteticas), "int8 sempre melhor" (depende do regime), "float32 obsoleto"
   (e o ORACLE — mante-lo salvou a arquitetura).

## Prioridade #1 dele = FASE 1 (ja executada)
"Medir o caminho real do knowledge search" — se reduzir 1M candidatos para
100k antes do dot, ganha mais que otimizar o kernel. NOS JA FIZEMOS (L343):
400 queries reais, 100% full-scan do indice, 13.801 vetores/query, ~1ms,
regime cache. A producao nao tem 1M de candidatos — tem 13.8k (L3).

## A visao estrutural do professor (proximo degrau do Cosca)
- Scientific Engine (estatistica/evidencia/incerteza) SEPARADO do Decision
  Engine: Scientific diz "o que os dados indicam", Decision diz "o que o
  sistema esta autorizado a fazer". Nunca deixar correlacao estatistica virar
  verdade arquitetural automaticamente.
- Evidencia com grau de realidade: VERIFIED_FOR_THIS_CONFIGURATION — contexto
  (hardware/dataset/condicoes) viaja junto com a medicao. Nunca "int8 = 4x".
- Aprendizado por refutacao: hipotese rejeitada = conhecimento (H1 CPU-bound
  REJECTED, H2 bandwidth SUPPORTED) — economiza experimentos repetidos.
- Conhecimento condicional (IF/THEN) em vez de memorizacao.
- Fronteiras descobertas por experimento (threshold V-Cache ~110k +- X).
- Loop OUTCOME: decisao -> resultado -> revisao (decisao certa no papel pode
  falhar na producao).
- Regras de contenção (12): hipotese != fato; contexto viaja com evidencia;
  baseline preservada; canary antes de promover; N medicoes com dados crus;
  "mais rapido" != "melhor" (multi-objetivo); ORACLE imutavel (float32);
  experimento rejeitado nao se apaga; separar descoberta de decisao;
  confianca rica (scope+sample+counter-evidence); declarar o que NAO sabe.
- Regra do topo: memoria != verdade, repeticao != evidencia, correlacao !=
  causalidade, hipotese != fato, benchmark != universalidade, confianca !=
  certeza. Quanto maior o impacto, maior a exigencia de evidencia
  independente.

## Decisoes da campanha
- Errata no relatorio: "limite fisico" -> "limite deste regime".
- Proximas fases na ordem do professor: FASE 3 (curva V-Cache/cache_budget),
  FASE 8 (recall real — fechar a lacuna "qualidade boa mas incompleta"),
  FASE 7 (int16 — candidato a melhor default com recall ~float32).
- NAO atacar o assembly enquanto ~40 GB/s (regra do professor = nossa L340).
- Formalizacao do Scientific/Evidence System = projeto estrutural futuro,
  com as 12 regras de contenção como constituicao.
