| **Learned** | **(1) O sistema de plugins do Backstage é o padrão ouro de extensibilidade enterprise — 150+ plugins, 71 packages, 3 gerações de API coexistindo (v1 core-plugin-api → v2 frontend-plugin-api → v3 extension tree).** A chave é a tríade Plugin-Module-ExtensionPoint: o plugin declara contratos, módulos de terceiros implementam, a plataforma resolve o grafo e injeta. **(2) O ServiceRef DI Container com escopos (root/plugin) e cardinalidade (singleton/multiton) resolve o problema de "quem cria o quê e quem pode acessar o quê" — sem framework de DI pesado, apenas tipagem forte e um motor de resolução de ~500 linhas.** O `InternalServiceFactory` com `deps` map explícito elimina dependências implícitas. **(3) A árvore de extensões frontend (Extension Tree) é o padrão mais avançado de composição declarativa que vimos: cada extensão declara onde se conecta (`attachTo`), o que produz (`output: Array<ExtensionDataRef>`), e o que consome (`inputs`).** O motor resolve o grafo, ordena topologicamente, e chama `factory()` de cada nó com inputs já resolvidos. Isso é como um DAG de workflow, mas para composição de UI. **(4) O Catalog Processing Pipeline com `CatalogProcessor.emit()` é superior ao nosso pipeline de workflow (L153) em um aspecto: o callback `emit(entity, relation, error, refresh)` permite que UM processor produza MÚLTIPLOS resultados de tipos diferentes.** Nosso StepRunner atual é 1:1 (um step → um resultado). **(5) O Scaffolder combina 4 padrões em 1: template engine (Nunjucks), command pattern (TemplateAction), workflow runner (TaskSpec.steps), e checkpoint idempotente (ActionContext.checkpoint).** O checkpoint é elegante: salva resultado em DB, retorna cache em retry — nosso Recovery Loop (L153) deveria adotar isso. **(6) O Permission Framework com AND/OR/NOT e dual apply()/toQuery() é o que falta para evoluirmos do JWT binário para autorização condicional: "agente X pode executar workflow Y se tipo=fix-bug E confiança>0.7".** `PermissionCriteria` com composição booleana + `toQuery()` que gera SQL é genial. **(7) O Event System Tri-Modal (local/auto/always) com bridging e long-polling é o padrão de resiliência progressiva: dev usa local puro, staging usa auto com fallback, produção usa always com garantia.** Nossos agentes não têm barramento de eventos — o kernel é o hub implícito. Um barramento explícito permitiria agentes reagirem a eventos sem acoplamento. **(8) O Test Harness multi-DB com `TestDatabases.eachSupportedId()` rodando o mesmo teste em SQLite, PostgreSQL, e MySQL no CI é o padrão anti-surpresa de compatibilidade SQL.** `ServiceFactoryTester` com DI isolado testa uma factory sem levantar o sistema inteiro. **(9) O modelo Entity Kubernetes-Inspired unifica todos os recursos sob {apiVersion, kind, metadata, spec, relations} — agents, skills, patterns, learnings poderiam ser kinds de entidade com relações.** Já temos graph (L163) — falta o modelo de entidade unificado. **(10) Opaque Type Discriminators ($$type) são runtime type safety em linguagens que apagam tipos em runtime (TS → JS, Go interfaces) — deveríamos adotar para agent registration, skill validation, plugin loading.** |
