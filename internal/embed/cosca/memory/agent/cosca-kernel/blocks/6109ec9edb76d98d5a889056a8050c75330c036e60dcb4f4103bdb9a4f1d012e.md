# L354 — Investigacao do chunker JSON (READ-ONLY, causa raiz encontrada)

## Caso minimo reproduzivel
JSON indentado (> MaxTokens 512) como texto puro -> ChunkDocument produz
1.500 chunks de ~15 chars (1 por linha do JSON); 1.200 fragmentos <=25 chars;
302 triviais filtrados pelo L353 (20%).

## Pipeline exato onde ocorre a fragmentacao
Parse (markdown) -> NodeParagraph POR LINHA -> chunker 1 chunk por no.
O parser markdown (internal/markdown Parse, default:) cria UM NodeParagraph
para CADA linha do conteudo — linhas consecutivas sem blank line NAO sao
agrupadas (divergencia do CommonMark, que agruparia num paragrafo unico).
O splitLongParagraph, quando recebe o bloco inteiro, AGUPA corretamente
(9 chunks de 2.550 chars) — o splitter NAO e o problema.

## Causa raiz
O PARSER MARKDOWN fragmenta por linha. JSON indentado = 1 no/linha = 1
chunk/linha. O CountTokens (chars/4) e o agrupamento funcionam; o parser
e o gargalo estrutural.

## Evidencias
- doc 4b87339a (dashboard JSON): 1.013 chunks, 694 (68%) <=25 chars, 141
  triviais puros ("{", "}") — um JSON virou ~1.000 embeddings de fragmentos.
- 253 fragmentos triviais JSON no corpus, 36 com vetor.
- Repro: 1.500 chunks / 1.200 fragmentos / 302 triviais filtrados.
- Controle: splitLongParagraph direto = 9 chunks (agrupamento OK).

## Impacto medido
- Cada JSON ingerido polui o indice com ~1.000 embeddings de 1 linha
  (fragmentos sem contexto do documento).
- L353 filtra os triviais puros (302/1800 = 20%) mas os fragmentos com
  alfanumericos ("\"builtIn\": 1,") continuam (KEEP).
- Fragmentos no top-K: improvável (score baixo) mas poluem RAM/scan e o
  recall de conteudo (jaccard).

## Separacao PROBLEMA A vs B
PROBLEMA A (triviais) -> L353 ja impede novos. PROBLEMA B (fragmentacao
por linha) -> L354 causa raiz = parser markdown; correcao em L355.

## Alternativas de correcao (nao implementar)
A) Parser markdown agrupa linhas consecutivas sem blank line em UM paragrafo
   (padrao CommonMark) — corrige na raiz; risco: muda o chunking de TODO o
   markdown (regressao possivel em docs normais — exigiria validacao ampla).
B) Chunker agrupa nos de paragrafo consecutivos (merge no ChunkDocument)
   — escopo menor (so o chunker); risco: mescla paragrafos de secoes
   diferentes (perde fronteiras de heading).
C) Detectar JSON (parse heuristico) e tratar como bloco unico — escopo
   focado; risco: falso positivo em texto parecido com JSON; fallback.
D) Agrupar no parser apenas quando a linha nao e heading/code/list etc.
   (conservador) — meio-termo entre A e B.

## Testes necessarios (para L355)
- Parser: linhas consecutivas sem blank line = 1 no; blank line = novo no.
- JSON indentado e minificado -> poucos chunks (1-9), nao 1.500.
- Texto normal com pontos/URLs preservado ("v1.2.3", https://...).
- Headings/code blocks/listas nao afetados.
- Regression: docs markdown existentes (paridade de chunking).

## Proposta futura
L355: avaliar A/B/C/D com dry-run de regressao (chunking de uma amostra de
docs reais ANTES vs DEPOIS); decidir por evidencia; implementar com flag
reversivel. Nao tocar o historico.
