## O MECANISMO (EVIDENCE — indexer.go:664-668)
O storeDocument DELETA os chunks antigos do documento ("DELETE FROM chunks
WHERE document_id = ?") ANTES do loop do dedup. Os canonicos (os chunks da
1a indexacao — os unicos com o conteudo identico) sao removidos ANTES do
dedup procurar -> dedup_of=0 -> TODOS os chunks re-embedados.
CONCLUSAO: o dedup preventivo (L372) so cobre o dedup ENTRE documentos —
NAO a re-indexacao do MESMO documento.

## O que isso significa (a conclusao LIMITADA)
- o dedup pre-embed (por hash, ANTES do embed) eliminaria 100% do embed
  redundante (99.6% da re-indexacao) — ~1.8s de 7.1s (~25%)
- MAS o custo DOMINANTE da re-indexacao e o FTS rebuild + o graph (~5s
  dos 7.1s — o achado #2/#5 do L387) — o dedup pre-embed SOZINHO nao
  resolve a re-indexacao
- o par completo: dedup pre-embed + FTS incremental + graph debounce
