> **Generated by**: cosca-performance (Performance Chief)

> **Quality Gate**: G7 (Performance Baseline — benchmarks sem degradação >10%)

## Executive Summary

This is the first quantified performance baseline for the Cosca platform. Previously, all performance hypotheses were derived from architecture, not measurement. We now have empirical data on the search pipeline latency, memory allocations, and CPU hot paths.

**Key Findings:**

1. **Vector search is the primary bottleneck** — brute-force cosine similarity scales linearly O(n): 542 µs @ 100 vectors → 64 ms @ 10,000 vectors. With 46.8 MB allocations per query at 10K vectors, this is the most urgent optimization target.

2. **FTS5 content-sync schema has a column mismatch** — `documents_fts` declares `content` column via `content='documents'` but the `documents` table has no `content` column. This causes `SQL logic error: no such column: T.content` on real FTS5 queries against documents_fts.

3. **Dashboard query (`GetStats`) performs 6+ separate DB roundtrips** — `COUNT(*)` on documents, chunks, entities, vectors + vector stats + graph stats + cache stats. No batching or caching.

4. **Search pipeline overhead is low but allocation-heavy** — ~33 µs/op for graph search (187 allocs), ~43 µs/op for vector path (329 allocs), ~67 µs/op with 100-result deduplication (530 allocs).

**Analysis — FTS5 Architecture (Static)**:
- FTS5 search is per-table sequential: queries all 4 tables (documents_fts, chunks_fts, code_blocks_fts, entities_fts) in a loop
- Each table gets: 1 SELECT query + 1 COUNT(*) query = 8 queries per search call
- `snippet()` and `highlight()` FTS5 functions are called per-row (expensive for large result sets)
- `SanitizeFTSQuery()` wraps each term in double quotes (creates new strings per call)
- **Schema bug found**: `documents_fts` uses `content='documents'` (content-sync) but `documents` table has no `content` column → runtime error `no such column: T.content`

### 1.3 Vector Similarity Search (sqlite-vec)

| Benchmark | Vectors | Latency | Memory/op | Allocs/op | Scaling Factor |
|-----------|---------|---------|-----------|-----------|----------------|
| 100 vectors | 100 | 541.8 µs | 438 KB | 3,819 | 1.0× (baseline) |
| 500 vectors | 500 | 2.32 ms | 2.16 MB | 19,022 | 4.3× |
| 1,000 vectors | 1,000 | 4.67 ms | 4.45 MB | 38,026 | 8.6× |
| 5,000 vectors | 5,000 | 30.4 ms | 22.9 MB | 190,033 | 56.1× |
| 10,000 vectors | 10,000 | 64.1 ms | 46.8 MB | 380,036 | 118.3× |

**Analysis**:
- **Brute-force implementation confirmed** — O(n) linear scaling with vector count
- Each search reads ALL vectors from DB, deserializes BLOBs, computes cosine similarity, and sorts in-memory
- **Memory usage is quadratic** relative to vector count due to: (a) loading all float64 slices, (b) allocating SearchResult structs, (c) sorting
- For 10K vectors: 46.8 MB per query — this is unsustainable for production dashboard queries
- **No ANN index** — the `VectorStats()` method reports `IndexType: "flat_bruteforce"`

**Hot path (per vector)**:
1. `rows.Scan()` — SQLite BLOB read
2. `bytesToFloat64Slice()` — binary decode (1024 B allocation per 128d vector)
3. `CosineSimilarity()` — float64 dot product + magnitude
4. Struct allocation for `SearchResult`
5. `sort.Slice()` — in-memory sort of all results

## 2. Bug-005 Performance Root Cause

### 2.1 Original Bug-005

Bug-005 (`bug-005-sqlite-first-run.md`) was a **SQLite migration panic on first run** — `getCurrentVersion()` called `panic()` when `schema_version` table didn't exist. This was **fixed** in commits `0ffb4da` and `c30fac3`.

### 2.2 Semantic Index Report: "Slow Dashboard Query"

The scorecard (`GAP-06`) references a semantic index report linking a "slow dashboard query" to bug-005 territory. After code analysis:

**Root cause hypothesis: The `documents_fts` FTS5 content-sync table has a schema mismatch that causes query failures.**

```sql
-- Schema (sqlite/schema.go:237-244)
CREATE VIRTUAL TABLE IF NOT EXISTS documents_fts USING fts5(
    title,
    content,          -- ← FTS5 expects content column...
    doc_type,
    tokenize='porter unicode61',
    content='documents',  -- ...from the 'documents' table
    content_rowid='rowid'
);

-- But the 'documents' table (sqlite/schema.go:47-59) has NO 'content' column!
CREATE TABLE IF NOT EXISTS documents (
    id TEXT PRIMARY KEY,
    path TEXT NOT NULL UNIQUE,
    hash TEXT NOT NULL,
    title TEXT NOT NULL DEFAULT '',
    doc_type TEXT NOT NULL DEFAULT 'markdown',
    -- NO 'content' column here!
    metadata_json TEXT NOT NULL DEFAULT '{}',
    ...
);
```

**Impact**:
1. `documents_fts` search queries return **0 results for document content** — the `SELECT title, content, doc_type FROM documents_fts` in `fts.go:93-98` fails with `SQL logic error: no such column: T.content` when rowid references a `documents` row
2. Document-level FTS search is **silently broken** for content queries
3. Only `chunks_fts` (which correctly references `chunks.content`) returns actual full-text results
4. The `countQuery` for `documents_fts` also fails silently

**Validation**: Confirmed in benchmarks — `BenchmarkFTS5SearchDocuments` reports:
```
warn: fts search documents_fts: SQL logic error: no such column: T.content (1)
```

**This is NOT a performance bug — it's a correctness bug masquerading as performance.** The "slow dashboard query" may have been reported because dashboards that should find document matches via FTS5 are finding nothing (or finding results only from chunks/entities), leading users to run broader queries that scan more tables.

### 2.3 Additional Performance Issues Found

| Issue | Location | Severity | Description |
|-------|----------|----------|-------------|
| **N+1 dashboard roundtrips** | `knowledge.go:410-483` (`GetStats`) | Medium | 6 separate DB queries to build dashboard stats — no batching |
| **Brute-force vector search** | `sqlite_vec.go:171-250` | High | O(n) full scan, no ANN index, 46.8MB/query @ 10K vectors |
| **Dual query per FTS search** | `fts.go:86-188` | Medium | Each FTS table gets SELECT + COUNT(*) = 8 queries per search call |
| **No stats caching** | `knowledge.go:410` | Medium | `GetStats()` computes everything from scratch each call |
| **Sync full-walk** | `knowledge.go:716-926` | Medium | `Sync()` walks entire filesystem + queries all documents — no incremental approach |

### Top 5 Functions by Complexity/Allocation Weight

| # | Function | File | Issue | Impact |
|---|----------|------|-------|--------|
| 1 | `SQLiteVec.SearchWithFilter` | `vector/sqlite_vec.go:171` | Full table scan + deserialize + cosine + sort | O(n·d) per query |
| 2 | `FTSClient.searchTable` | `sqlite/fts.go:86` | COUNT(*) + MATCH query, snippet()/highlight() per row | 2 queries per table |
| 3 | `Engine.GetStats` | `knowledge/knowledge.go:410` | 6 roundtrips + graph serialization | Sequential I/O |

| 5 | `CosineSimilarity` | `vector/vector.go` (inferred) | Float64 dot product + magnitude per comparison | O(d) per comparison |

### Allocation Hotspots

Based on benchmark data:
1. **Vector search results**: 38K allocs/query @ 1K vectors, 380K @ 10K vectors — `SearchResult` structs + `[]float64` slices
2. **FTS snippet/highlight**: `snippet()` and `highlight()` SQL functions create new strings per row
3. **Search result dedup**: `map[string]bool` + `append` on `allResults` slice = amortized copies
4. **Embedding function call**: `embedFunc()` path creates closures and copies (external provider call)

## 5. Top 3 Quick-Win Optimizations

### 5.1 🥇 Fix `documents_fts` Schema Mismatch (Effort: 2h, Impact: Critical)

**Problem**: `documents_fts` references a `content` column that doesn't exist in `documents` table.

**Fix** (choose one):
- **Option A (preferred)**: Remove `content='documents'` from `documents_fts` and index documents by title + doc_type only (since documents have no body content — content lives in chunks)
- **Option B**: Add a `content` column to `documents` table (migration needed, increases DB size)

**Impact**:
- ✅ Fixes silent FTS search failures for document queries
- ✅ Restores expected search behavior for document-level queries
- ✅ Eliminates `SQL logic error: no such column: T.content` runtime warnings

### 5.2 🥈 Add ANN Index to Vector Store (Effort: 16h, Impact: High)

**Problem**: Vector search uses brute-force cosine similarity — full table scan every query. At 10K vectors: 64ms latency, 46.8 MB allocs, 380K allocs.

**Fix**: Integrate an approximate nearest neighbor (ANN) index. Options:
- **FAISS** (C++ library via CGO): Mature, battle-tested, supports IVF/HNSW
- **usearch** (pure C, single-header): Lightweight, no heavy dependencies
- **sqlite-vec with virtual tables**: If sqlite-vec supports this (check extension docs)
- **HNSW in pure Go**: Small code, well-understood algorithm

**Impact**:
- ✅ Expected: 100-1000× speedup for vector search (64ms → <1ms)
- ✅ Drastically reduced memory (no full table load)
- ✅ Enables scaling to 100K+ vectors

### 5.3 🥉 Implement Dashboard Stats Caching (Effort: 4h, Impact: Medium)

**Problem**: `GetStats()` issues 6 separate DB queries on every call with no caching.

**Fix**:
1. Add a 5-second TTL cache for stats in the Engine struct
2. Invalidate on index/rebuild events
3. Use `sync.RWMutex` for concurrent reads

```go
type Engine struct {
    // ... existing fields ...
    statsCache     *Stats
    statsCacheTime time.Time
    statsCacheTTL  time.Duration // 5s
}
```

**Impact**:
- ✅ Eliminates 6 DB roundtrips per dashboard refresh in steady state
- ✅ 100× improvement for dashboard load — from ~13µs of queries to ~100ns of cache read
- ✅ Zero memory overhead (one Stats struct, ~200 bytes)
