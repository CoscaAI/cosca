# GOVERNANCE — Versioning, Lifecycle & Deprecation

> **Version**: 1.0.0 | **Status**: active | **Owner**: Cosca Kernel

## Purpose
Define how Cosca skills, engines, workflows, and templates are versioned, maintained, and retired. This is the single source of truth for governance policies.

---

## Versioning Policy

### Semantic Versioning (SemVer)

All Cosca files follow **X.Y.Z** format:

| Part | Bump When |
|------|-----------|
| **X** (Major) | Breaking changes to skill contract, inputs, or outputs |
| **Y** (Minor) | New section, new responsibility, new specialist added |
| **Z** (Patch) | Clarifications, typo fixes, formatting improvements |

### Version History

Every file tracks changes in its `HISTORY` section:

```markdown
## HISTORY

| Version | Date | Author | Changes |
|---------|------|--------|---------|
| 1.0.0 | YYYY-MM-DD | name | Initial release |
| 1.1.0 | YYYY-MM-DD | name | Added X section |
| 1.0.1 | YYYY-MM-DD | name | Fixed typo in Y |
```

## Lifecycle States

```
  ┌─────────┐
  │  DRAFT  │  → Under active development, may change frequently
  └────┬────┘
       │ Approved
       ▼
  ┌─────────┐
  │  ACTIVE  │  → Production-ready, used by agents
  └────┬────┘
       │
       ├──→ No longer needed
       │
       ▼
  ┌────────────┐
  │ DEPRECATED  │  → Still available, migration notice issued
  └────┬───────┘
       │ After migration period
       ▼
  ┌──────────┐
  │ RETIRED   │  → Removed from active registry
  └──────────┘
```

| State | Meaning | Agent Behavior |
|-------|---------|---------------|
| **draft** | Work in progress | Do not load into production context |
| **active** | Production-ready | Normal loading and execution |
| **deprecated** | Scheduled for removal | Load with deprecation warning |
| **retired** | Archived | Never load, file moved to `archive/` |

## Deprecation Policy

### When to Deprecate
- Skill is superseded by another skill
- Department is merged or restructured
- Workflow is replaced by new version
- Template no longer relevant

### Deprecation Process
1. Mark status as `deprecated` in metadata
2. Add deprecation notice at top of file
3. Specify replacement (if any)
4. Set sunset date (minimum 30 days)
5. Update COSCA_INDEX.md
6. Announce in CHANGELOG.md

### Deprecation Notice Format
```markdown
> ⚠️ **DEPRECATED** since YYYY-MM-DD. Will be retired after YYYY-MM-DD.
> Migration path: Use [replacement-file.md] instead.
```

## Compatibility Policy

### Backward Compatibility
- **Patch versions** (0.0.X): Always backward compatible
- **Minor versions** (0.X.0): Backward compatible for inputs/outputs; new sections allowed
- **Major versions** (X.0.0): May break compatibility; requires migration guide

### Breaking Changes
A change is breaking if it:
1. Removes a mandatory section
2. Changes input format
3. Changes output format
4. Renames the file
5. Removes a specialist type
6. Changes the skill's purpose

Breaking changes require:
- Major version bump
- Migration guide
- 30-day deprecation period for old version
- Notification to all dependent skills

## Ownership

### Owner Types
| Type | Description |
|------|-------------|
| **Department** | Department chief owns department SKILL.md |
| **Engine** | Engine owns its SKILL.md |
| **Cosca Kernel** | Owns governance docs, INDEX, CHANGELOG |
| **Workflow Chief** | Owns workflow definitions |

### Owner Responsibilities
1. Review skill annually for relevance
2. Update version on every change
3. Maintain HISTORY section
4. Respond to deprecation requests
5. Fix quality issues found by Evolution Engine

---

## Change Approval

| Change Type | Approval Required |
|-------------|-------------------|
| Patch (typo, formatting) | Owner only |
| Minor (new section, new specialist) | Owner + reviewer |
| Major (breaking changes) | Owner + CTO + affected departments |
| New skill/file | CTO approval + CONVENTIONS compliance |
| Deprecation | Owner + CTO |
| Retirement | Owner + CTO + 30-day notice |

## Audit & Compliance

The Evolution Engine periodically audits:
- [ ] All files have metadata block
- [ ] All files have valid version number
- [ ] No deprecated files past sunset date
- [ ] All active files have HISTORY entries
- [ ] Cross-references are valid
- [ ] No duplicate responsibilities
- [ ] CONVENTIONS.md compliance score > 80%
